# v2.0 Realtime Public-State Architecture Plan

**Status:** Provisional direction; proof of concept required

**Decision date:** August 31, 2026

**Release target:** v2.0, only if every promotion gate passes

**Current production architecture:** Unchanged; Neon plus adaptive polling
remains authoritative and supported

**Candidate architecture:** Neon-authoritative state with one Cloudflare
Durable Object public hub per agency

## Decision statement

LOTTO will investigate a Cloudflare Durable Object realtime hub as the
provisional architectural direction for v2.0. The hub would retain the latest
allowlisted public queue projection and broadcast versioned state to connected
public clients over hibernatable WebSockets. Neon would remain authoritative
for authenticated commands, atomic state changes, undo/restore snapshots,
authentication, configuration, translations, and administrative reporting.

This is not yet a final architecture decision. A major-version release is
appropriate only after the candidate proves that it improves public freshness
and Neon scale-to-zero behavior without weakening state integrity, recovery,
security, legacy-device compatibility, or the current app's ability to operate
when the hub is unavailable.

Until the final v2.0 gate passes:

- the current `/api/state` read/write behavior remains the production baseline;
- adaptive polling remains implemented, tested, and deployable;
- no production staff command may depend on Cloudflare availability;
- all database changes must be additive and backward-compatible;
- realtime activation must be independently reversible by environment and
  client cohort; and
- a failed experiment returns the project to the current architecture without
  data migration or emergency code removal.

## Why this warrants v2.0

The change introduces a second runtime, a public event-delivery protocol,
cross-system publication, version reconciliation, realtime connection state,
and new operational failure modes. Even though the existing user workflows can
remain visually familiar, the way public state reaches every Home, Display,
Inventory, and Arcade surface changes fundamentally.

The major version is reserved for the proven architecture, not for the proof of
concept. Experimental and shadow-mode work may land during v1.x while disabled
by default. v2.0 is not cut merely because the prototype connects successfully.

## Goals

1. Reflect a committed staff state change on connected public clients in
   near-real time.
2. Eliminate ordinary `/api/state` polling while a realtime connection is
   healthy.
3. Prevent public traffic from waking Neon or extending its active-compute
   window.
4. Preserve Neon transactionality, snapshots, undo/redo, and state recall.
5. Keep public state an explicit allowlisted projection, never a serialized
   copy of the complete internal `RaffleState`.
6. Make every cross-system operation idempotent, versioned, observable, and
   recoverable.
7. Preserve the current application as the automatic fallback throughout
   development and after release.
8. Keep incremental infrastructure cost within a documented nonprofit budget
   and measure it under realistic always-on display usage.

## Non-goals for the initial v2.0 architecture

- Moving authentication, translations, brand configuration, snapshots, or
  reporting out of Neon.
- Making Durable Object storage the authoritative queue database.
- Replacing the current Admin workflow or changing queue semantics.
- Using Neon logical replication, `LISTEN`/`NOTIFY`, or another long-lived
  database subscriber; those approaches can prevent Neon from scaling to zero.
- Removing polling before the realtime path has completed production canary
  validation.
- Guaranteeing literal zero infrastructure cost. Free allowances have hard
  limits and do not provide the same reliability guarantees as paid service.
- Adding gameplay traffic or Arcade state to the queue-state hub.

Promoting the Durable Object itself to authoritative operational storage is a
possible post-v2 investigation. It is explicitly outside this plan because it
would move transaction and recovery ownership away from the proven Neon state
manager.

## Current and candidate flows

### Current production flow

```text
public client ──poll──> Vercel /api/state ──query──> Neon

staff action ─────────> Vercel /api/state ──transaction──> Neon
```

### Candidate v2.0 flow

```text
                                  ┌──versioned state──> Home
                                  ├──versioned state──> Display
staff action                      ├──versioned state──> Inventory
    │                             └──versioned state──> Arcade banner
    ▼                                      ▲
Vercel authenticated command               │ WebSocket
    │                                      │
    ▼                                      │
Neon transaction ──after commit──> Cloudflare Worker
  current state                      │
  snapshot/history                   ▼
  monotonic revision             Durable Object
  publication outbox             latest public state
                                  connected clients

If realtime is unavailable: client immediately resumes the current bounded
polling strategy; staff commands continue to commit to Neon.
```

## Architectural invariants

These rules apply in every experimental phase and are release blockers if
violated.

1. **Neon commits first.** Public state is never broadcast before the
   authoritative transaction commits.
2. **One authority.** During v2.0, Neon decides the current queue state. The hub
   is a derived read model.
3. **Staff writes survive hub failure.** A Cloudflare timeout or outage cannot
   roll back or reject a state change that Neon committed successfully.
4. **Monotonic public revisions.** A client or hub never replaces a newer
   revision with an older one.
5. **Idempotent publication.** Repeating a publication produces the same final
   state and does not create a second logical transition.
6. **Explicit public schema.** Internal evidence such as `queueSession`, auth
   data, snapshot metadata, translation credentials, and Admin-only fields
   never enter the hub.
7. **Subscribe-only public clients.** Browsers cannot publish authoritative
   queue events.
8. **No unbounded background loops.** The Worker, Durable Object, and client do
   not use fixed perpetual timers to simulate reliability.
9. **Fallback remains bounded.** Connection failure can activate the existing
   adaptive polling strategy, including visibility pause, operating-hour
   cadence, error backoff, and request-budget tests.
10. **Protocol compatibility is explicit.** Client and hub exchange a
    `protocolVersion`; incompatible clients fall back instead of guessing.

## Candidate system boundaries

### LOTTO Next.js application on Vercel

Responsibilities:

- authenticate and authorize staff commands;
- execute the authoritative Neon transaction;
- increment the authoritative state revision;
- write publication intent in the same transaction;
- serialize the allowlisted public projection;
- sign and send a post-commit publication request;
- expose publication health to Admin without making it a prerequisite for a
  successful queue action; and
- retain the current read endpoint and polling behavior as fallback.

### Neon Postgres

Responsibilities:

- authoritative current queue state;
- atomic snapshots, undo/redo, and restore history;
- monotonic revision allocation;
- publication/outbox evidence;
- authentication and configuration stores; and
- authoritative recovery if the public hub is lost or rebuilt.

The implemented additive candidate gives the singleton `raffle_state` row an
authoritative `BIGINT` revision and records publication ID, revision, protocol
version, checksum, allowlisted payload, attempt state, timestamps, and a bounded
error summary in `raffle_public_state_publications`. It remains inert while the
shadow-publication flag is off.

### Cloudflare Worker and Durable Object

Responsibilities:

- route an agency's requests to one Durable Object using a stable opaque agency
  identifier;
- authenticate server-to-server publication;
- reject malformed, oversized, unsigned, replayed, or out-of-order updates;
- store only the newest valid public projection and protocol metadata;
- accept public read-only WebSocket connections;
- send the current projection on connection;
- broadcast a committed newer revision to connected clients;
- use the WebSocket Hibernation API so idle connections do not require active
  JavaScript duration; and
- emit operational metrics without visitor identity or ticket-search data.

There must be one object per agency, not one global singleton for every LOTTO
deployment. Development, preview, and production use distinct Worker
environments/namespaces so experimental state cannot cross boundaries.

### Public clients

Responsibilities:

- connect with the native browser WebSocket API;
- subscribe before resolving initial state so updates cannot fall into a
  fetch/subscribe race;
- compare every message revision with local state;
- ignore duplicates and older revisions;
- apply a full newer public projection atomically;
- fetch/resume fallback state on an invalid message, revision gap, unsupported
  protocol, or connection failure;
- expose a restrained connection status (`Live`, `Reconnecting`, or
  `Fallback`) where operationally useful; and
- stop ordinary state polling only after realtime has been declared healthy.

The initial implementation should broadcast the complete bounded public
projection rather than client-side deltas. Full state is easier to reason about,
idempotent, and recoverable. Delta messages should be considered only if
measured payload size or fanout cost requires them.

## Candidate protocol

The protocol is intentionally small. Exact names can change during the contract
phase, but these semantics must remain.

| Field             | Purpose                                                      |
| ----------------- | ------------------------------------------------------------ |
| `protocolVersion` | Reject incompatible client/hub behavior safely               |
| `agencyId`        | Route and validate tenant identity without exposing a secret |
| `publicationId`   | Idempotency and trace correlation                            |
| `revision`        | Monotonic authoritative state version                        |
| `committedAt`     | Authoritative Neon commit time                               |
| `publishedAt`     | Hub acceptance time for latency measurement                  |
| `checksum`        | Detect equal-revision payload conflicts or corruption        |
| `state`           | Allowlisted `PublicRaffleState` projection                   |

Candidate message types:

- `state`: current complete projection, sent on connection and after updates;
- `resync-required`: hub cannot safely establish continuity;
- `status`: optional protocol/service notice that carries no queue mutation; and
- `error`: bounded non-sensitive protocol failure information.

Revision handling at the hub:

- incoming revision greater than stored: validate, store, then broadcast;
- equal revision and equal checksum: return idempotent success;
- equal revision and different checksum: reject and alert as an integrity
  conflict;
- lower revision: do not store or broadcast; return the hub's current revision;
  and
- no stored revision: accept only an authenticated publication or report empty
  state to public clients so they enter fallback.

## Publication and recovery model

Postgres and Durable Object storage cannot share a transaction. The design uses
transactional intent plus idempotent delivery instead of claiming distributed
atomicity.

1. The authenticated action validates an optional command idempotency key and
   expected revision.
2. The Neon transaction applies the state change, writes its snapshot/history,
   increments revision, and records publication intent.
3. After commit, the Vercel handler attempts to publish the new public
   projection synchronously within a strict timeout.
4. Success records the accepted hub revision.
5. Failure leaves the authoritative action committed and the publication
   pending. Admin receives a non-destructive “public sync delayed” status.
6. Bounded retry uses the same publication ID and revision. Retryable failures
   use exponential backoff; overload signals do not trigger a retry storm.
7. A later staff action, an explicit Admin repair action, or an approved
   event-driven delivery mechanism drains only the newest necessary pending
   state. A fixed cron that repeatedly wakes Neon is not an acceptable repair
   strategy.
8. The hub's revision is periodically compared with the authoritative revision
   through staff/admin activity and deployment health checks, not visitor
   polling.

The prototype must compare at least three delivery choices before hardening:

- direct bounded post-commit publish plus outbox repair;
- Cloudflare Queue handoff after commit, with the Neon outbox retaining the
  pre-enqueue failure evidence; and
- Vercel-supported deferred work only if its retry/durability semantics meet the
  same requirements.

No option removes the final network gap after a database commit. The acceptance
criterion is visible, idempotent convergence—not an impossible exactly-once
claim.

## Security model

Public queue state is intentionally readable, but its integrity remains
security-sensitive.

- Use `wss://` only.
- The public WebSocket endpoint accepts subscriptions but no state mutation.
- The isolated beta proof currently authenticates publication with one
  least-privilege bearer secret, an exact beta-host allowlist, and a beta-only
  runtime gate. Rotate that secret before integrated testing.
- Before any production shadow canary, decide whether to replace the proof
  bearer with a server-to-server signature over method, path, agency ID,
  timestamp, nonce, and body digest.
- If signatures are adopted, enforce a short replay window, reject reused
  nonces, and support signing-key IDs with overlapping rotation.
- Store signing secrets only in Vercel and Cloudflare secret stores, never in a
  `NEXT_PUBLIC_*` variable or browser bundle.
- Validate the public-state schema and a conservative serialized payload limit
  before storage or fanout.
- Apply per-IP connection/rate controls and a per-agency connection ceiling.
- Ignore or close unexpected client frames rather than echoing them.
- Do not log ticket searches, session identifiers, email addresses, auth tokens,
  full state payloads, signatures, or secret material.
- Treat `Origin` checking as abuse reduction, not authentication; non-browser
  clients can forge it.

Threat-model and security review are required before the first production
canary.

## Feature flags and rollback controls

Activation must be decomposed so publishing, connecting, and stopping polling
are never one irreversible switch.

| Capability                    | Default before proof | Purpose                                            |
| ----------------------------- | -------------------- | -------------------------------------------------- |
| Hub service deployed          | Development only     | Exercise Worker/DO independently                   |
| Server publication            | Off                  | Shadow-copy committed public state                 |
| Client WebSocket connection   | Off                  | Observe connection behavior without changing reads |
| Client applies realtime state | Off                  | Compare pushed versus polled revisions             |
| Healthy client stops polling  | Off                  | Realize the cost reduction only after canary proof |
| Connection-status UI          | Internal/canary only | Diagnose without changing general workflow         |

A runtime capability response should be preferred over relying exclusively on
build-time `NEXT_PUBLIC_*` flags. A loaded client must automatically resume
polling if its connection fails even when a kill-switch deployment has not yet
reached that browser.

Rollback sequence:

1. Disable realtime application/connection for the affected cohort.
2. Clients resume the existing polling strategy immediately.
3. Disable server publication if the hub or protocol is the incident source.
4. Leave additive revision/outbox fields in place; they do not affect current
   state reads or writes.
5. Investigate from version/health metadata without deleting authoritative data.

## Production-shaped beta environment

The preferred integration and canary environment is a separate deployment at
`https://beta.williamtemple.app`, not a preview attached to the live WTH Vercel
project. This directly addresses the current production project's Preview
database-variable gap and provides a stable origin for WebSocket, authentication,
PWA, CSP, DNS, and legacy-device testing.

The beta hostname is only the visible entry point. Production-like testing
requires isolation at every stateful boundary:

| Layer          | Production                                 | Beta requirement                                                                                              |
| -------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| App            | WTH Vercel project at `williamtemple.app`  | Separate Vercel project at `beta.williamtemple.app`                                                           |
| Git promotion  | Production branch                          | Explicit beta/staging branch selected during provisioning                                                     |
| Database       | WTH production Neon database               | Fresh beta Neon database with schema plus synthetic/sanitized data                                            |
| Blob assets    | Production Appearance store                | Separate beta Blob store/token                                                                                |
| Authentication | Production secret, tokens, and auth tables | Separate secret and auth tables; host-only beta cookies                                                       |
| Email          | Production Resend configuration            | Separate beta API key/configuration; beta callback URL and clearly labeled messages                           |
| Realtime       | Not deployed initially                     | Deployed `lotto-realtime-beta` Worker and separate SQLite-backed Durable Object namespace                      |
| Hub origin     | Future production endpoint                 | `https://lotto-realtime-beta.et2-geiger.workers.dev`; custom beta realtime DNS remains optional and unprovisioned |
| Metrics/logs   | Production projects                        | Separate beta Vercel, Neon, and Cloudflare views                                                              |

The beta database must not be the production database. A fresh database is
preferred over an unsanitized branch because queue snapshots, authentication
records, integration credentials, translation API configuration, and other
operational data must not be copied into an experiment by default. Apply the
canonical `schema.sql`, seed synthetic queue history, and recreate only the
Appearance/configuration necessary for representative testing.

The beta deployment must also:

- use `AUTH_URL=https://beta.williamtemple.app` and a distinct `AUTH_SECRET`;
- verify that auth/session cookies remain host-only and do not cross between the
  apex and beta origins;
- keep beta Magic Link and OTP callbacks on the beta origin;
- use a separate Blob store so Appearance experiments cannot overwrite live
  assets;
- allow the beta app origin—and only that origin—on the beta hub's WebSocket
  abuse-control allowlist;
- add the beta WebSocket host to the beta CSP `connect-src` without broadening
  production CSP early;
- prevent indexing with a beta-specific `X-Robots-Tag`/robots policy;
- display an unmistakable non-production banner on staff/admin surfaces;
- prohibit production FEED credentials or irreversible external integrations;
- use independent spend alerts and the lowest practical Cloudflare limits; and
- avoid placing the Vercel app behind a Cloudflare proxy unless proxying the
  application itself becomes an explicit experiment. The app and realtime hub
  are separate origins and can be tested that way.

Promotion moves reviewed code, protocol versions, schema migrations, Worker
configuration, and runbooks. It never promotes beta queue data, auth rows, Blob
objects, Durable Object storage, or secrets into production.

Suggested environment progression:

1. local Next.js plus local `wrangler dev`;
2. Vercel beta project plus remote beta Worker/DO and beta Neon;
3. stable `beta.williamtemple.app` canary with selected physical devices;
4. production shadow publication with no production realtime clients;
5. production opt-in canary; and
6. v2.0 release candidate only after the beta and production gates pass.

## Measurement model

The experiment needs an explicit baseline and comparable post-change window.

### User-visible service objectives

Candidate promotion targets:

- p50 Neon-commit-to-client-render latency at or below 500 ms on a stable local
  network;
- p95 at or below 2 seconds and p99 at or below 5 seconds;
- reconnect and latest-state reconciliation within 5 seconds after a usable
  network returns;
- no visible regression to an older revision; and
- a clear fallback state instead of a frozen apparently-live display.

These are experiment targets, not promises. The baseline study may refine them
before production canary.

### Correctness objectives

- 100% agreement between Neon and the hub's newest revision/checksum at every
  completed validation checkpoint;
- zero public broadcasts for rolled-back/failed Neon transactions;
- duplicate and reordered deliveries converge to the newest state;
- every injected publication failure is visible and recoverable;
- undo, redo, restore, reset, and all other mutation types publish a new
  monotonic revision; and
- hub loss/recreation can be seeded safely from Neon.

### Resource objectives

- zero `/api/state` requests from a client during a one-hour healthy realtime
  test;
- at least 95% fewer public-origin state reads during the production canary;
- materially longer Neon suspended intervals outside authenticated work;
- no short repeating Durable Object alarms, timers, or application heartbeats
  that defeat hibernation;
- current-load Cloudflare usage remains inside the approved trial allowance;
  and
- a documented projected cost at 1×, 10×, and 100× current connected-client and
  state-change volume.

Free-tier success is not the production cost criterion. Workers Free fails
operations when a hard limit is exceeded. The final recommendation must include
the paid-plan floor, spend alerts, and the fallback behavior when a limit is
reached.

## Multi-phase delivery plan

Every phase ends with a written result and explicit go/no-go decision. Passing a
phase authorizes only the next phase, not the complete architecture.

### Phase 0 — Baseline, requirements, and experiment charter

**Objective:** establish what the candidate must beat and freeze the current
behavior as a protected fallback.

**Work:**

- Gather 7–14 representative days of Neon CU-hours, active/suspended windows,
  storage/history, and public network use.
- Record Vercel `/api/state` invocations, Edge Requests, transfer, response size,
  and latency by open/closed period.
- Measure connected/visible client counts and state changes per service day.
- Inventory every public state consumer and every state mutation path.
- Define `PublicRaffleState` fields and an initial size budget.
- Record current polling request-count tests and fallback behavior.
- Set the trial budget and Cloudflare account/ownership model.
- Decide the initial latency, convergence, uptime, and canary-duration targets.

**Exit gate:** baseline dataset, approved experiment budget, public-field
inventory, measurable success criteria, and an explicit statement that current
production behavior is unchanged.

**Rollback:** none required; this phase is read-only documentation and
measurement.

### Phase 1 — Protocol and local state-machine experiment

**Objective:** prove revision and reconciliation semantics without Cloudflare or
production data.

**Work:**

- Build a framework-neutral public projection serializer and schema.
- Model publication IDs, monotonic revisions, checksums, duplicate delivery,
  reordered delivery, revision gaps, and unsupported protocols.
- Build a small in-memory/local hub and a test client using the native WebSocket
  contract or a transport-neutral simulator.
- Determine whether the shared protocol belongs in a small workspace package or
  in isolated LOTTO/Worker modules with generated schemas and contract tests.
- Establish serialized-size limits using realistic maximum queue states.

**Required tests:** serializer allowlist, protected-field exclusion, payload
limit, idempotency, out-of-order rejection, equal-revision conflict, gap
recovery, full-state atomic application, and protocol-version fallback.

**Exit gate:** deterministic contract tests prove that arbitrary duplicate and
reordered messages cannot regress client or hub state.

**Rollback:** remove or retain the isolated experiment; no production path or
schema has changed.

### Phase 2 — Standalone Cloudflare proof of concept

**Objective:** prove the platform characteristics with synthetic state and no
LOTTO integration.

**Work:**

- Create a development-only Worker and SQLite-backed Durable Object.
- Use one object per synthetic agency and the Hibernation WebSocket API.
- Store a bounded latest projection and send it immediately on connection.
- Add a development publication endpoint with production-shaped signature and
  replay checks.
- Exercise local `wrangler dev` behavior and a remote development deployment.
- Measure connect, first-state, broadcast, hibernation/wake, and reconnect
  behavior.
- Evaluate Cloudflare's automatic ping/pong or WebSocket auto-response support
  before adding any application heartbeat.
- Enable development logs/metrics with payload redaction.

**Required tests:** 1/10/100/200 concurrent synthetic clients, rapid updates,
idle hibernation, cold wake, Worker redeploy, network interruption, duplicate
publish, invalid signature, replay, oversized payload, malformed frame, and
object recreation.

**Evidence checkpoint — August 31, 2026:** The repeatable
`realtime:load` harness opened 1, 10, 100, and 200 concurrent clients in four
bounded groups against the remote beta Worker (311 connections and four
publications total). Every client received its target revision. The one-run
measurements were:

| Clients | Connect p50 / p95 / max | Delivery p50 / p95 / max | Delivered |
| ------- | ----------------------- | ------------------------ | --------- |
| 1 | 269 / 269 / 269 ms | 69 / 69 / 69 ms | 1 / 1 |
| 10 | 121 / 155 / 155 ms | 57 / 59 / 59 ms | 10 / 10 |
| 100 | 427 / 538 / 548 ms | 120 / 137 / 138 ms | 100 / 100 |
| 200 | 994 / 1,079 / 1,088 ms | 159 / 194 / 198 ms | 200 / 200 |

These figures prove bounded fanout functionality from one test location; they
are not production latency claims. Repeat runs, sustained connections, rapid
updates, hibernation/wake, interruption, and device testing remain open.

**Synthetic A/B checkpoint — September 1, 2026:** The new
`realtime:benchmark` runner compares equal polling and WebSocket cohorts against
the dedicated `william-temple-house-benchmark-e2e` object, using identical
checksummed revisions. Its first local run used 10 clients per cohort, five
publications, and a one-second synthetic polling cadence. All 50 expected
deliveries per cohort converged with no checksum mismatch. Aggregate polling
latency was 499.82 ms p50 and 997.18 ms p95; aggregate realtime latency was
3.62 ms p50 and 5.63 ms p95. The polling cohort made 50 snapshot reads during
the measured changes; the healthy realtime cohort made zero recurring snapshot
reads after its 10 initial connections.

This local result proves the runner and the expected transport distinction. It
does not prove internet latency, Durable Object hibernation, Vercel request
reduction, or Neon compute savings. Those claims require a bounded remote run
with platform metrics and the Phase 3/4 application integration described
below. Full commands, safety caps, report fields, and interpretation live in
`docs/REALTIME_BENCHMARK.md`.

The first remote beta A/B run used the same 10-client/five-publication
configuration. All 50 deliveries per cohort converged; polling measured 504.88
ms p50 and 996.95 ms p95, while realtime measured 73.06 ms p50 and 78.58 ms
p95. A separate realtime-only probe then held five WebSockets open for 60
seconds with no polling or snapshot request to its object. All five clients
received the post-idle revision with 88.16 ms p95 and no checksum mismatch.
This demonstrates request-free idle survival and successful subsequent
delivery. Cloudflare metrics must still establish whether the Durable Object
actually hibernated during that window.

**Legacy proof:** connect an iOS 15.4 simulator and the real iPad mini 4 to the
remote `wss://` development service; leave it idle, background/foreground it,
interrupt Wi-Fi, and confirm recovery on the physical screen.

**Exit gate:** the raw platform meets provisional latency and reconnection
targets, hibernation is visible in metrics, estimated cost is acceptable, and
no client SDK threatens the legacy bundle.

**Rollback:** delete the development Worker/namespace after exporting results;
LOTTO remains untouched.

### Phase 3 — Additive Neon revision and shadow publication

**Objective:** integrate real committed state while no public client trusts the
hub.

**Work:**

- Provision the isolated `beta.williamtemple.app` stack described above before
  using real application integrations.
- Add backward-compatible revision/publication metadata to the database.
- Increment revision and record publication intent inside every state-changing
  transaction.
- Publish the allowlisted projection only after commit.
- Store it in the beta Durable Object namespace.
- Keep all public clients on `/api/state` polling.
- Compare authoritative and hub revision/checksum after every test action.
- Add Admin/internal diagnostics for publication status without changing the
  staff action's success semantics.
- Inject timeouts and failures to select the bounded retry/repair mechanism.

**Required coverage:** every action in the state API, including generate,
append, range changes, serving advance/reverse, Returned/Unclaimed/revert,
reset, restore, undo, redo, hours, rotation, display URL, and announcement.

**Implementation checkpoint — September 1, 2026:** The local, disabled-by-default
slice is complete enough for beta schema validation. `raffle_state.revision`
and `raffle_public_state_publications` are additive and idempotent. Every
database mutation still converges on the existing `persist()` transaction,
which now allocates the revision and inserts the allowlisted, checksummed
outbox row atomically when enabled. After commit, one request with a 100–5,000
ms bounded timeout may publish to the exact beta Worker host. A hub or evidence
update failure cannot reject the committed staff action. Explicit repair reads
only the newest pending/failed full state, revalidates its strict public schema
and checksum, and reuses its original idempotency identity. Internal status
returns metadata without the payload or secret. Focused tests cover disabled
zero-work behavior, transaction shape, accepted/rejected publication,
evidence-update failure, timeout, redacted network errors, newest-only repair,
and invalid stored evidence. The schema has not yet been applied to beta Neon,
the flag remains off, and no deployment claim is made.

**Exit gate:** the beta app completes full-stack auth, command, Neon, publish,
WebSocket, CSP, and fallback checks; a representative staging run shows complete
revision agreement;
failed/rolled-back transactions never publish; all injected delivery failures
are visible and repairable; disabling publication leaves current behavior
unchanged.

**Rollback:** disable server publication. Additive database fields remain inert;
the existing state manager and polling clients continue normally.

### Phase 4 — Dual-read internal canary

**Objective:** connect selected clients while polling remains the displayed
source of truth.

**Work:**

- Add a shared realtime client hook behind a runtime cohort flag.
- Run the first browser cohort on `beta.williamtemple.app`; do not connect
  production public clients during the initial comparison.
- Subscribe and record pushed revisions, but continue rendering polled state.
- Compare pushed versus polled revision, payload checksum, and arrival time.
- Exercise Home, Display, Inventory celebration, and Arcade banner consumers.
- Add restrained internal connection diagnostics.
- Verify background-tab behavior and that reconnects do not create overlapping
  sockets or polling loops.

**Exit gate:** pushed state matches authoritative polled state across all
surfaces and wins the latency comparison without increasing errors, memory, or
legacy-device failures.

**Rollback:** turn off client connection for the cohort. No user-visible source
of state has changed.

### Phase 5 — Realtime-source canary with polling safety net

**Objective:** let a small controlled cohort render realtime state while
retaining automatic fallback.

**Work:**

- Apply pushed state for designated staff test devices and one display.
- Stop scheduled polling only after connection plus initial-state handshake is
  healthy.
- On close, timeout, invalid payload, gap, or kill switch, fetch immediately and
  resume adaptive polling.
- Reconnect with bounded exponential backoff and jitter; pause connection work
  appropriately while hidden without compromising a fixed visible kiosk.
- Show a clear non-alarming fallback status during tests.
- Run deliberate Cloudflare, Vercel, and Neon fault scenarios.

**Exit gate:** at least 10 representative service days with no stale-regression
incident, all failure drills recover, staff writes never depend on hub health,
and canary clients generate no healthy-state `/api/state` polling.

**Rollback:** disable realtime application for the cohort. The hook immediately
returns to the existing polling source.

### Phase 6 — Limited production rollout and cost validation

**Objective:** prove the system at real agency scale without declaring v2.0.

**Work:**

- Expand gradually by surface or percentage: Display, then Home, then Inventory
  and Arcade banner.
- Retain a control cohort on polling for latency and correctness comparison.
- Run for at least 30 calendar days including ordinary closed periods,
  deployments, network interruptions, and staff undo/restore operations.
- Compare Neon active time/CU-hours and Vercel request usage with the Phase 0
  baseline.
- Measure Cloudflare connections, requests, duration, storage, errors, and
  projected paid-plan exposure.
- Set spend notifications and a documented response to quota/limit exhaustion.
- Complete security review and operational runbooks.

**Exit gate:** final service objectives pass, public-origin Neon reads fall by at
least 95%, cost is within the approved envelope, and the control/realtime cohorts
show no correctness divergence.

**Rollback:** return all cohorts to polling; disable publication if needed. Neon
remains complete and authoritative.

### Phase 7 — v2.0 implementation hardening and release candidate

**Objective:** convert a successful experiment into supported architecture.

**Work:**

- Remove experimental diagnostics while retaining actionable health status.
- Finalize protocol compatibility and Worker deployment/versioning policy.
- Finalize key rotation, agency provisioning, rebuild-from-Neon, incident,
  quota, and rollback runbooks.
- Update `docs/DEPLOYMENT.md`, `docs/SECURITY.md`, `docs/BROWSER_SUPPORT.md`,
  `docs/POLLING.md`, relevant `docs/user-guides/`, environment examples, schema
  documentation, and release notes.
- Ensure public consumers use one shared realtime/fallback hook.
- Keep adaptive polling as a tested degraded mode; do not delete it.
- Complete full regression, load, chaos, security, and legacy-device suites.
- Deploy a v2.0 release candidate to Vercel Preview and the production-shaped
  Cloudflare environment.

**Exit gate:** all final release gates below pass and the architecture decision
record changes from provisional to accepted.

**Rollback:** do not release v2.0. Continue the proven v1.x production path or
select another public-delivery architecture using the experiment evidence.

### Phase 8 — Post-release observation

**Objective:** make promotion reversible during the early supported period.

- Preserve polling fallback and kill switches through at least the first stable
  v2.x observation window.
- Review latency, reconnection, Neon compute, and Cloudflare cost weekly at
  first, then monthly.
- Do not promote Durable Object storage to queue authority without a separate
  architecture plan and major data-migration review.

## Final v2.0 release gates

The provisional decision becomes accepted only when all of the following are
true:

- the production canary completes its full observation window;
- public state reaches stable connected clients within the accepted latency
  objectives;
- Neon and hub revision/checksum comparisons show no unexplained divergence;
- all mutation, undo, restore, and reset paths publish correctly;
- Cloudflare loss never prevents an authoritative staff action;
- automatic fallback succeeds in every supported public surface;
- healthy clients produce no ordinary `/api/state` polling;
- public-origin Neon reads fall by at least 95% versus baseline;
- current and projected Cloudflare cost fit the approved budget;
- hard quota behavior is known and documented;
- security review and secret rotation pass;
- the simulator and real iPadOS 15 device pass;
- deployment, recovery, rebuild, rollback, and incident runbooks are exercised;
- relevant user guides describe any visible connection/fallback behavior; and
- the current polling implementation remains available as supported degraded
  mode.

Failure of a gate does not require forcing the design through. The experiment
may revise the protocol, repeat a phase, adopt a managed realtime provider, fall
back to tagged CDN delivery, or conclude that current polling remains the better
operational tradeoff.

## Open decisions for the proof program

These are experiments to resolve, not reasons to guess before Phase 0:

1. Whether a direct signed publish plus Neon outbox is sufficient or a
   Cloudflare Queue is justified.
2. Whether protocol code should be a small shared workspace package or separate
   modules governed by generated schema and contract tests.
3. The maximum serialized public-state payload and whether a full state message
   remains economical at 100× load.
4. How quickly a browser should declare a silent connection unhealthy without
   adding wakeful application heartbeats.
5. Whether connection status belongs on all public surfaces or only operational
   Display/Admin diagnostics.
6. Whether one shared multi-agency Worker or per-agency Worker deployments offer
   the better security, provisioning, and cost boundary.
7. The approved paid-plan/fallback behavior when Workers Free limits are
   approached or exceeded.
8. What caused the January 2026 Blob experiment rollback and which lessons apply
   to any derived public-state store.
