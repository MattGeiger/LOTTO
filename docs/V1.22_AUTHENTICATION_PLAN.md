# LOTTO v1.22.0 Authentication Implementation

## Outcome

Bring FEED's improved passwordless sign-in experience to LOTTO while preserving
LOTTO's Auth.js/Postgres architecture and runtime white-label system. Magic Link
becomes the default because it is now safe behind Microsoft Defender and other
email-scanning gateways; Verification Code remains a first-class fallback.

## Design Pressure

Before v1.22.0, LOTTO exposed Auth.js Magic Links directly. A security scanner's
GET could consume a single-use token before staff clicked it. OTP email used a
separate, lightly branded delivery path; its request deleted all verification
tokens for an address, including pending Magic Links. The login UI also moved
to code entry after a failed request and described a ten-minute Magic Link even
though the provider used Auth.js's longer default.

## Approaches Considered

### 1. Make Verification Code the only method

- **Advantage:** avoids scanner behavior entirely.
- **Cost:** removes the lower-friction workflow, diverges from FEED, and does
  not improve the email identity or shared delivery architecture.

### 2. Replace Auth.js email authentication with a custom token system

- **Advantage:** total control over every callback and data row.
- **Cost:** duplicates mature session/token behavior, expands security review,
  and introduces a new authentication framework boundary for one scanner issue.

### 3. Preserve Auth.js and interpose a human confirmation step — selected

- **Advantage:** keeps the current adapter, session, authorization, and
  deployment model. Automated GETs are harmless; only a deliberate POST reaches
  the native email callback. This matches FEED's proven contract.
- **Cost:** adds one intentional click and makes the callback wrapper a
  security-sensitive compatibility seam that must be tested when Auth.js moves.

## Implemented Slices

### Slice 1 — Shared branded delivery

- Resolve the active compiled or saved brand on the server at send time.
- Convert brand colors to email-safe hex values.
- Render Magic Link and Verification Code through one React Email shell and
  generate both HTML and plain-text bodies.
- Use the deployment's verified `EMAIL_FROM`, with the runtime app name as the
  display name, and keep Resend/SMTP fallback behavior in one service.

### Slice 2 — Scanner-safe Magic Link callback

- Intercept GET requests to `/api/auth/callback/resend` (and the compatible
  `email` provider id).
- Copy token, email, and callback destination into `/login/confirm` without
  delegating to Auth.js.
- Render a static confirmation page with no effect or automatic submission.
- Submit an explicit POST to the same Auth.js callback only when staff press
  **Sign in**.

### Slice 3 — Token isolation and explicit expiry

- Add `verification_token.type` with an additive `magic_link` default.
- Mark OTP rows as `otp`; delete and consume only that type.
- Set both authentication methods to a ten-minute expiry in shared constants so
  provider behavior, UI text, and email copy cannot silently drift.

### Slice 4 — Sign-in interaction

- Put **Magic Link** first and make it the default.
- Rename **OTP Code** to the clearer **Verification Code**.
- Keep delivery/authorization failures on the email step with actionable inline
  feedback; show code entry only after a successful request.
- Preserve the email value across method switches and provide correct browser
  autocomplete hints.

## Security Invariants

- A GET never consumes a Magic Link token.
- The confirmation page never auto-submits.
- A Magic Link and OTP for the same address can coexist.
- Only allowed staff emails can request or complete either method.
- Tokens and codes are never embedded in application logs.
- Runtime brand content is escaped by React Email; sender addresses reject
  header-breaking characters.
- Existing sessions, users, and verification rows survive the additive schema
  migration.

## Acceptance Coverage

- Repeated Magic Link GETs redirect without calling Auth.js.
- Non-email Auth.js GETs and all callback POSTs still delegate normally.
- Both built-in brands render recognizable HTML and plain-text email bodies.
- Verification Code failures do not show a false “Code sent” state.
- OTP issuance/consumption queries are type-scoped.
- Full tests, lint, legacy-bundle validation, and production builds pass for
  William Temple House and St. Johns profiles.

## Deployment Sequence

1. Apply the full idempotent `schema.sql` to each agency's Neon database.
2. Confirm the new token column and index exist.
3. Deploy v1.22.0 without changing `AUTH_SECRET`, `EMAIL_FROM`, or existing
   authorization policy.
4. Request a Magic Link, open/refresh its confirmation page, then press **Sign
   in** and confirm `/admin` loads.
5. Request and complete a Verification Code.
6. Repeat request rejection with an unauthorized address and inspect delivery
   for correct agency identity in HTML, plain text, and an image-blocking mail
   client.

Rollback to v1.21.1 is code-compatible with the additive schema: older Auth.js
inserts receive the `magic_link` default and older queries ignore the column.
