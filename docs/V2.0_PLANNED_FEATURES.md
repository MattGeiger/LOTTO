# v2.0 Planned Features

**Status:** Planning (revised scope)
**Release intent:** v2.0 major upgrade
**Scope:** Staff login + authenticated navigation, an announcement builder, an
AI configuration / translation system and expanded localization (both ported
from the FEED project), ticket-status revert, and a new Arcade game ("Pantry
Time").

> **Note on scope history:** the *original* v2.0 plan was the **Arcade track**
> (dedicated `/arcade`, NOW SERVING banner, Snake, retro visuals) plus the
> personalized homepage and `/display` board. That work **shipped** across
> v1.5–v1.16 and is recorded under
> [Delivered — Arcade Track](#delivered--arcade-track-original-v20-scope) below.
> v2.0 has been **re-scoped** to the six features in
> [v2.0 Revised Scope](#v20-revised-scope) — the new headline work.

---

## Summary

The original v2.0 **Arcade** vision (dedicated `/arcade`, persistent NOW SERVING
banner, Snake + Brick Mayhem + Day of the Dead, retro 8-bit visuals, the
personalized `/` homepage, and the `/display` board) has **all shipped** in
v1.5–v1.16. See [Delivered — Arcade Track](#delivered--arcade-track-original-v20-scope).

The re-scoped v2.0 delivers six features, several of which **port proven code
from the FEED project** (`/Users/russbook/williamtemple-feed`):

1. **Revised login + authenticated navigation** — replace `/staff` with a
   FEED-style login; show authenticated staff an ADMIN / DASHBOARD / INVENTORY /
   GAMES nav.
2. **Announcement builder** — admin-authored, markdown-formatted announcement
   shown as a homepage onboarding step.
3. **AI translation** — port FEED's AI configuration, encryption, and translation
   stack.
4. **Expanded localization** — enable any of FEED's 59 languages on top of the
   hardcoded set, auto-translated via the AI stack.
5. **Ticket-status revert** — make Returned/Unclaimed tickets revertible.
6. **"Pantry Time"** — a Burger Time–style game on the existing sprite engine.

Full per-feature plans, FEED source references, and the implementation ranking
are in [v2.0 Revised Scope](#v20-revised-scope).

`src/components/navigation/bottom-tab-bar.tsx` + `nav-items.tsx`, but as

### Feature 2 — Announcement builder

**What.** From `/admin`, staff can toggle an **announcement pop-up**. A simple
editor stores **markdown** with toolbar controls (Bold, Italic, Underline,
Titles, Bullets, Numbered lists) and a live rendered preview. Exactly **one**
announcement persists at a time, with a **start/end date-time** window. When
enabled, homepage visitors see the announcement as a **third onboarding step**
(after language selection, before ticket entry).

**Borrow.**
- FEED has **no** announcement feature — this is net-new. Reuse the
  already-ported markdown renderer
  `src/components/help/markdown-guide.tsx` (`MarkdownGuideContent`,
  `react-markdown` + `remark-gfm`) for the preview and the modal render.
- Onboarding flow to extend: `src/components/personalized-home-page.tsx`
  (today's two-step language→ticket modal).
- Persistence + snapshots: `src/app/api/state/route.ts`,
  `src/lib/state-manager*.ts`, `src/lib/state-types.ts`.

**Build.** A toolbar editor (no FEED/3rd-party WYSIWYG to borrow — FEED edits
prompts with plain textareas). Implement a lightweight markdown toolbar over a
`textarea` (insert `**`, `_`, `#`, `-`, `1.`, etc.) with `MarkdownGuideContent`
preview. Extend `RaffleState` with an `announcement` field (markdown, enabled,
start, end) and a `setAnnouncement` API action (reuse atomic write + snapshots).
Add the announcement step to the onboarding modal.

**Effort/Deps.** Medium. The localized text comes from Feature 3 (English-only
until then).

### Feature 3 — AI translation (configuration, encryption, providers)

**What.** Port FEED's AI configuration + translation system. Authenticated users
**initialize encryption**, then configure AI **models + API keys**. System
prompts and model settings are a **shared** setting for all authenticated users.
When enabled, announcement text is **auto-translated** into the enabled languages
and shown per the client's language preference.

**Borrow (FEED) — backend services (framework-agnostic TS, port to LOTTO server/lib).**
- `packages/backend/src/services/encryption/key-manager.ts` (`KeyManager`) —
  encryption initialization / key sealing for stored API keys.
- `packages/backend/src/services/ai/providers/{AnthropicTranslationService,OpenAITranslationService,GoogleTranslationService}.ts`
  — provider adapters + per-provider supported-language sets.
- `packages/backend/src/services/translation-trigger.ts`,
  `translation-recovery.ts`, `translation-auditor.ts` — translation
  orchestration, retries, gap detection.
- `packages/backend/src/services/token/`, `services/limits/`,
  `config/translation.ts` — token accounting and cost limits.
- `packages/backend/src/routes/{ai-config,translations,system-prompts,languages}.ts`
  — endpoint behavior to re-expose as Next route handlers.

**Borrow (FEED) — frontend AI config UI.**
- `packages/frontend/src/components/ai-configuration/*` — the whole suite:
  `setup/InitialSetupWizard.tsx`, `form/AIConfigurationForm.tsx`,
  `AddAIModelDialog.tsx`, `EditAIModelDialog.tsx`, the system-prompt dialogs,
  `steps/*`, `data-table/*`, `model-specs.ts`, `hooks/{useSetupState,useSystemStatus}.ts`,
  `shared/BaseAIConfigDialog.tsx`.

**Build (LOTTO).** FEED's backend is Express + Prisma + SQLite; LOTTO is Next API
routes + Neon Postgres. Port the **services** (encryption, providers, translation
orchestration) into `src/lib/ai/*` and expose via new `src/app/api/ai-config/*`
and `src/app/api/translations/*` route handlers. Add Neon tables for AI config,
encrypted keys, system prompts, and a translation cache. Port the config UI into
a new `/admin` AI Configuration section using LOTTO's shadcn/ui primitives and
App Router conventions.

**Effort/Deps.** Large (biggest item). Foundational for Feature 4 and for
announcement localization in Feature 2.

#### Feature 3b — Translation Management (resilience)

**What.** AI translation requests can **fail** or **stall in pending**. FEED
solves this with a Translation Management layer that **stores** every
translation, lets staff **correct** them, **retry** failed/stuck ones, and run a
**"Find Missing Translations"** audit. LOTTO must port this so localization is
trustworthy (Features 2 and 4 depend on it).

**Borrow (FEED) — backend.**
- `packages/backend/src/services/translation-auditor.ts` — **Find Missing
  Translations**: audits all content × enabled languages, reports gaps by
  type/language, and optionally creates + queues the missing ones (also used when
  a new language is enabled).
- `packages/backend/src/services/translation-recovery.ts` — detects and retries
  **stuck/pending** translations (one automatic recovery attempt per item).
- `packages/backend/src/routes/translations.ts` — endpoint behaviors to
  re-expose as Next route handlers: `POST /find-missing`, `POST /recover-stuck`,
  `POST /:id/retry`, `POST /bulk-retry`, `PUT /:id` (manual correction),
  `GET /metrics`, `GET /performance`, plus list/CRUD/bulk-delete.

**Borrow (FEED) — frontend.**
- `packages/frontend/src/components/translation-management/*` — the management
  UI: `index.tsx`, `TranslationList/`, `data-table/`, `edit-dialog.tsx` (manual
  correction), `retry-dialog.tsx`, `find-missing-dialog.tsx`,
  `enhanced-find-missing-dialog.tsx`, `add-dialog.tsx`, `delete-dialog.tsx`,
  `form/`, `utils/`, `types.ts`.

**Build (LOTTO).** A `translations` table in Neon keyed by (content key, language)
with a **status** (`pending` / `complete` / `failed`) and the translated text;
the AI calls from Feature 3 write through it (so a failure is recorded, not
lost). Port the auditor + recovery as `src/lib/ai/translation-auditor.ts` /
`translation-recovery.ts`, expose the routes above under
`src/app/api/translations/*`, and port the management UI into the `/admin`
Translation Management section. For LOTTO the "content" set is the UI string keys
(Feature 4) plus the active announcement (Feature 2).

**Effort/Deps.** Medium-Large; part of the Feature 3 workstream (build alongside
the AI stack). Directly de-risks Features 2 and 4.

### Feature 4 — Language settings & expanded localization

**What.** Reuse FEED's language settings + translation to go beyond LOTTO's eight
hardcoded languages. Hardcoded translations stay as-is; authenticated users can
**enable additional languages** (e.g. Bosnian). Enabling a language triggers AI
translation of all mapped UI strings; once complete, clients can select it
alongside the hardcoded options. With **>10** total languages, apply a
**scroll area** to language selection (onboarding modal **and** dropdown).

**Borrow (FEED).**
- `packages/frontend/src/config/language-config.ts` — the 59-language
  `SUPPORTED_LANGUAGES` list (and `DEFAULT_ACTIVE_LANGUAGES`).
- `packages/frontend/src/components/language-management/*` — enable/disable UI,
  `language-filter.tsx`, `language-deactivation-dialog.tsx`; FEED `LanguagePage`
  (route in `App.tsx`).
- `packages/backend/src/routes/languages.ts` — enabled-language persistence +
  the translation-trigger hook on enable.

**Build (LOTTO).** Today translations are a hardcoded map in
`src/contexts/language-context.tsx` (8 languages). Keep that as the base; add a
Neon-backed dynamic translation store for enabled languages, and make `t()` fall
back hardcoded → DB-translated → English. Enabling a language enumerates the
existing translation keys and AI-translates them (Feature 3) into the new
language. Add a `ScrollArea` to the switcher (`src/components/language-switcher.tsx`)
and the onboarding language step when options exceed 10. Reuse `src/lib/rtl-utils.ts`
and extend it for any new RTL languages.

**Effort/Deps.** Large. Depends on Feature 3.

### Feature 5 — Ticket-status revert (Returned / Unclaimed)

**What.** Make the ticket numbers in the **Returned** and **Unclaimed** cards

**Borrow.** LOTTO-only (no FEED). Mirrors the existing `markReturned` /

- `src/lib/state-manager.ts` / `state-manager-db.ts`, `src/lib/state-types.ts`.
- Returned/Unclaimed cards in `src/app/admin/page.tsx` (Live State lists);

**Effort/Deps.** Small. Self-contained quick win; no dependencies.

**Status: ✅ Implemented (Unreleased).** `revertTicketStatus` action in
`src/app/api/state/route.ts` + both state managers (`src/lib/state-manager.ts`,
`state-manager-db.ts`); interactive Returned/Unclaimed chips with a confirm

status without rewinding `currentlyServing`. Covered by

### Feature 6 — New game: "Pantry Time"

**What.** A Burger Time clone themed as a William Temple House food pantry:
steer a **shopping cart** through the pantry collecting food items while avoiding
hazards. Built on the **same sprite engine** as Day of the Dead.

**Borrow.** LOTTO-only (no FEED). Use the existing sprite engine as the template:
- `src/arcade/game/zombie-attack/{engine,renderer,types,constants,assets}.ts`
  — engine loop, sprite renderer, asset pipeline to clone into
  `src/arcade/game/pantry-time/*`.
- Route: `src/app/(arcade)/arcade/pantry-time/page.tsx`; add an entry to the
  arcade index (`src/app/(arcade)/arcade/page.tsx`). Follow the Arcade
  guardrails in `AGENTS.md` (keep it isolated from raffle code/UI).

**Build.** New game logic (cart movement, item collection, hazards, levels) and
new pixel-art assets; 8-locale strings like the other games.

**Effort/Deps.** Large (new game + art) but fully isolated; can run in parallel.

## v2.0 Product Goals

1. Make Arcade feel like its own mini-product area in both code and UX.
2. Preserve queue visibility by keeping **NOW SERVING** always visible during Arcade usage.
3. Ship a clean game-launch flow with Snake as the initial offering.
4. Establish a scalable foundation for adding future simple games.

### 1) Dedicated Arcade Surface
- Add a dedicated Arcade route and layout (`/arcade` and `/arcade/*`).
- Keep Arcade code isolated under Arcade-specific folders.

- Show a top banner with **NOW SERVING** on all Arcade pages.

- Banner should prioritize legibility and low cognitive load.

- Provide a simple game selection menu on `/arcade`.

- Keep Snake gameplay separate from raffle UI/state semantics.

- Apply pixel-art style graphics and UI treatment for Arcade surfaces.
- Keep this visual system scoped to Arcade.

- Evolve the personalized homepage (`/`, promoted from `/new` in v1.16.0) while preserving the current look-and-feel baseline.

1. **Always-visible NOW SERVING:** The top banner remains present during gameplay.
2. **Fast entry to play:** User can reach Snake in one tap/click from Arcade menu.
3. **Clear separation:** Arcade should not visually resemble raffle display/admin surfaces.
4. **Mobile first:** Menu and Snake controls must be usable in simulated mobile testing.

## Acceptance Criteria

- `/arcade` renders a game selection menu with a Snake launch button.
- `/arcade/snake` is playable and preserves the persistent top **NOW SERVING** banner.
- Arcade UI uses retro/pixel direction and does not reuse raffle-specific UI patterns.
- Arcade implementation remains isolated from raffle display component architecture.
- `/` is the personalized homepage and `/display` remains the unchanged public-board experience (personalization promoted from `/new` in v1.16.0).
- `/staff` board CTA routes to `/display` to preserve stable operations.
- Optional client-device haptics are available on Arcade and the personalized homepage (`/`) only for direct button-style interactions; the public board (`/display`) remains haptic-free.
- Design and behavior are validated in local mobile simulation before production rollout.

## Surface Material Tokens ("Glass" Design System)

**Status:** Planned (v2.0 design-system track)
**Motivation:** v1.7.x introduced translucent "glass" treatments (translucent
fill + backdrop blur) across the bottom nav, dropdowns, popovers, switchers, and
the `/new` dialog — applied surface-by-surface with ad-hoc Tailwind values
(`bg-card/[45%]`, `backdrop-blur-[6px]`, etc.; see `docs/UI_DESIGN.md` →
"Translucent Surface Materials"). The dialog exposed the limit of one-value-fits-all
glass: a `DialogContent` over the `bg-black/40` overlay is both blurred **and**
darkened, dragging down text contrast. The fix is to treat each surface class as
a *material* with several independent parameters (tint, alpha, blur, brightness,
saturation) tuned per surface and per theme — which ad-hoc utility classes
cannot express cleanly.

**Goal:** promote the per-surface material settings into discrete, theme-aware
**material tokens** in global CSS, consumed via a small set of `.material-*`
utility classes (or `data-material="…"`), replacing the ad-hoc inline values.

Sketch (illustrative, not final):

```css
:root {
  /* one token set per surface "material" */
  --glass-dialog-tint: var(--popover);
  --glass-dialog-alpha: 0.55;
  --glass-dialog-blur: 2px;
  --glass-dialog-brightness: 1.6;   /* lighten the darkened overlay (light mode) */
  --glass-dialog-saturate: 1.2;
  --glass-dialog-edge: 255 255 255; /* lit top-rim highlight color */
  --glass-dialog-edge-alpha: 0.5;
  /* shadow follows the project glow convention — reuse --base-shadow-color,
     do NOT hardcode a literal blue (see UI_DESIGN.md → Shadows) */
  /* …nav, dropdown, popover materials get their own sets… */
}
.dark {
  --glass-dialog-alpha: 0.5;
  --glass-dialog-brightness: 0.9;   /* dark mode biases the other way */
  --glass-dialog-edge-alpha: 0.12;
  /* dark shadow is a soft blue-teal GLOW (illuminate, not darken) */
}

.material-glass-dialog {
  background-color: hsl(var(--glass-dialog-tint) / var(--glass-dialog-alpha));
  backdrop-filter:
    blur(var(--glass-dialog-blur))
    brightness(var(--glass-dialog-brightness))
    saturate(var(--glass-dialog-saturate));
}
```

**In scope for this track:**

- A small material taxonomy (e.g. `nav`, `dialog`, `dropdown`, `popover`) with
  per-material token sets and light/dark overrides.
- `.material-*` utility classes (or a data-attribute) so components opt in by
  intent, not by hand-tuned values.
- Solve the dialog contrast problem with the "lighten + transparency + blur"
  stack (`backdrop-brightness` composed into `backdrop-filter`), scoped to the
  dialog material so other surfaces are unaffected.
- Include **edge-highlight** (lit top rim) and **soft ambient shadow** as
  material properties; the shadow must honor the dark-mode glow convention
  (soft blue-teal, reusing `--base-shadow-color`) rather than a black drop.
- Migrate the existing glassed surfaces off ad-hoc utilities onto the tokens.
- Honor `prefers-reduced-transparency` (and reduced-motion where relevant) by
  falling back to opaque tints.
- Keep the Arcade material separate (`--arcade-*`), per guardrails.

**Out of scope:** changing *which* surfaces are glassed (that stays a human
design judgement); restyling the Arcade pixel-art material.
